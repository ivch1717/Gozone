# Gozone

Микросервисное приложение для оформления заказов и асинхронной оплаты с внутреннего счёта. Основной фокус — Java backend: REST API, обмен событиями через Kafka, транзакционная обработка платежей и тестирование.

## Стек

| Область | Технологии |
| --- | --- |
| Backend | Java 25, Spring Boot 4.1, Spring Web MVC, Spring Data JPA / Hibernate, Spring Validation, Spring Kafka, Spring Boot Actuator |
| Данные и события | PostgreSQL, Apache Kafka, Jackson, Transactional Outbox / Inbox |
| Тестирование | JUnit 5, Mockito, AssertJ, MockMvc, JaCoCo |
| Инфраструктура | Maven Wrapper, Docker, Docker Compose, Nginx API Gateway |
| Дополнительно | SLF4J / Logback, React, Vite, lucide-react |

## Возможности

- Создание счёта, получение баланса и пополнение. Денежные суммы представлены через `BigDecimal`.
- Создание и просмотр заказов, пагинация и сортировка через `Pageable`.
- Асинхронная оплата: заказ переходит из `NEW` в `PAID` или `CANCELED` в зависимости от результата списания.
- Валидация запросов и доменных правил, централизованная обработка ошибок через `ControllerAdvice`, включая `404` и `409`.
- Логирование HTTP-запросов, времени выполнения и обработки событий; health checks через Actuator.

Рабочий интерфейс на **React** позволяет пройти весь сценарий: открыть счёт → пополнить баланс → создать заказ → увидеть результат оплаты. Есть переключение пользователя по UUID и автоматическое обновление статусов.

## Архитектура и обработка платежей

**Orders Service** управляет заказами, **Payments Service** — счетами и списаниями. У каждого сервиса своя PostgreSQL; взаимодействие происходит через Kafka, без прямого доступа к чужой БД. Nginx предоставляет единую точку входа для API и интерфейса.

Внутри сервисов выделены слои `api`, `application`, `domain` и `db`: контроллеры работают с DTO, сценарии выполняются в сервисах, бизнес-правила находятся в доменных моделях, а хранение — в JPA-сущностях и репозиториях. Мапперы отделяют представление API и БД от домена. Такое разделение упрощает тестирование, развитие функциональности и независимое изменение сервисов.

```text
Orders → Outbox → Kafka: payment-requests → Payments Inbox
                                               ↓
                                      списание со счёта
                                               ↓
Orders ← Kafka: payment-results ← Outbox ← результат оплаты
```

- **Transactional Outbox:** заказ и событие на оплату сохраняются в одной транзакции. Аналогично, списание и результат оплаты фиксируются вместе. Фоновый publisher отправляет события в Kafka и помечает их отправленными после подтверждения брокера; при ошибке событие остаётся для повторной попытки.
- **Inbox:** входящие заявки сохраняются в БД с дедупликацией по `eventId`. Повторная доставка того же события не создаёт новую заявку на списание.
- **Обработка ошибок:** некорректная заявка переводится в `FAILED` с сохранением причины и не блокирует следующие платежи. При отсутствии счёта или недостатке средств заказ отменяется.
- **Транзакции и блокировки:** при оплате счёт блокируется на время изменения баланса; повторный результат оплаты не меняет уже завершённый заказ.

## Запуск

Нужен Docker с поддержкой Linux-контейнеров и Docker Compose. Из корня проекта:

```shell
docker compose up --build -d --wait
```

**Приложение: [http://localhost:8085](http://localhost:8085).**

Compose собирает backend и frontend, поднимает PostgreSQL, Kafka, создаёт топики и запускает Gateway. Устанавливать Java, Maven или Node.js отдельно не требуется. Первый запуск может занять несколько минут.

API доступно через `/payments` и `/orders` на том же адресе. Настройки портов сервисов и пароли локальных БД можно изменить через `.env` по примеру [.env.example](.env.example). Данные сохраняются в Docker volumes.

Для демонстрации выберите UUID пользователя, откройте счёт, пополните его и создайте заказ. Переключение UUID служит для демо; авторизация и реальные платёжные системы не подключены.

## Тесты

Unit-тесты покрывают доменную логику, сервисы, мапперы, HTTP-контракты и обработку событий. Проверяются валидация, недостаток средств, дубликаты, переходы статусов, пагинация, ошибки API и повторная отправка Outbox. Контроллеры тестируются через **MockMvc**, внешние зависимости заменяются моками **Mockito**.

Запуск из корня проекта в PowerShell, нужен JDK 25+:

```powershell
.\orders-service\mvnw.cmd -f orders-service/pom.xml clean verify
.\payments-service\mvnw.cmd -f payments-service/pom.xml clean verify
```

**JaCoCo** формирует HTML-отчёты в `<service>/target/site/jacoco/index.html`. Сборка проверяет минимальное покрытие каждого сервиса: **85% строк и 90% ветвей**. Для unit-тестов не нужны запущенные PostgreSQL и Kafka.

После запуска контейнеров доступен отдельный smoke-тест полного сценария с реальными сервисами: успешная оплата, недостаток средств и отсутствие счёта.

```powershell
.\scripts\smoke-test.ps1
```
